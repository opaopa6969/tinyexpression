# テストスイート時間の削減（issue #200）

2026-09-25。`./mvnw test` が共有ホストの負荷次第で 15〜60 分かかり、2.0.0 のリリースが
`-DskipTests` を余儀なくされた問題への対処。issue #200 の仮説（「javac をその場で起動するのが
支配的」）を実測で検証したところ、**真の支配的コストは javac ではなく、6 つの `CalculatorImplTest`
派生スイートが同じ ~150 式を毎回、共通の legacy 文法パーサ（classic `FormulaParser`）で再検証している
重複だった**。この重複は純粋にテストコード側の問題であり、プロダクションのコンパイル/評価エンジン
（`JavaCodeCalculatorV2`/`V3`、`AstEvaluatorCalculator` 等）には一切手を入れずに解消できた。

## 1. 実測（このマシン、`load average` 6.5/32core 時点。issue 記載の 15〜25 load 時よりは軽い）

`mvn -B -o test -Dtest=<class>` を単体実行した秒数（surefire `Time elapsed`）。

| スイート | before | after (単体順*) | 削減率 |
|---|---:|---:|---:|
| `P4DslJavaCodeCalculatorTest`（javac 経由） | 112.8 s | **18.9 s** | -83% |
| `AstEvaluatorCalculatorTest`（AST、javac なし） | 97.6 s | 74.4 s（3スイート中で最初に実行され、初回コストを丸ごと負担） | -24% |
| `P4AstEvaluatorCalculatorTest`（AST、javac なし） | 89.9 s | **5.4 s** | -94% |
| 3 スイート合計（1 回の `mvn test` 呼び出し内） | 300.3 s | **105.0 s** | **-65%** |

\* Surefire は既定で 1 フォークを使い回す（pom.xml `reuseForks=true`）ため、同じ JVM 内で複数スイートを
続けて実行すると 2 本目以降がキャッシュの恩恵を受ける。この非対称性自体が「重複の存在」を裏付ける。

`CalculatorImplTest` の全派生 6 スイート（上記 3 つ + `P4DslJavaCodeCalculatorClassicEngineTest` /
`P4AstEvaluatorCalculatorClassicEngineTest` / `JavaCodeCalculatorV3Test`、classic エンジン系は
`P4ParserEngine`/probe timeout を意図的に無効化した重い経路）を 1 回の `mvn test` で流した場合:

```
Tests run: 294, Failures: 0, Errors: 0, Skipped: 12
AstEvaluatorCalculatorTest                    74.36 s  (先頭。全式ぶんの classic 文法検証を負担)
P4DslJavaCodeCalculatorClassicEngineTest      30.70 s
P4AstEvaluatorCalculatorTest                   5.89 s
P4DslJavaCodeCalculatorTest                   17.88 s
P4AstEvaluatorCalculatorClassicEngineTest     24.80 s
JavaCodeCalculatorV3Test                      16.95 s
合計テスト時間                                170.6 s（mvn 全体では 3m09s）
```

6 スイート全部が同じ ~150 式を再検証していた before の想定値（各スイート単体 90〜113 s 相当）と比べると、
2 本目以降が軒並み 1 桁〜30 s 台に落ちており、複数スイートを 1 回の `mvn test` にまとめて流すほど効果が
積み上がる（CI の `ubnfc-parser` ジョブは既に `P4DslJavaCodeCalculatorTest,P4DslJavaCodeCalculatorClassicEngineTest,
P4AstEvaluatorCalculatorTest,P4AstEvaluatorCalculatorClassicEngineTest` を 1 回の `mvn test` で回しており、
このジョブがそのまま恩恵を受ける)。

**full `./mvnw test`（全モジュール、フィルタなし、960 テスト / 146 クラス）**: この計測時は自己ホスト
ランナー（同マシン上の別ジョブ、`actions-runner-tinyexpression`）が実際に同時稼働しており、issue が
問題にしている「共有ホストの負荷」を再現した状態での実測になった。

```
Tests run: 960, Failures: 0, Errors: 0, Skipped: 14
Total time:  08:08 min
real    8m10.343s
```

issue 記載の before（15〜60 分）に対し、共有ホスト負荷ありの状態で **8 分 10 秒**。親タスクの目標
「full `./mvnw test` ≤ 15 min」を実負荷下でも達成した。

この全体実行内での `CalculatorImplTest` 系 6 スイートの内訳（パッケージ順で `evaluator.ast` が先頭を
引くため、その時点でキャッシュがまだ空で全額を負担している点に注意）:

| スイート | Time elapsed |
|---|---:|
| `AstEvaluatorCalculatorTest`（先頭、キャッシュ未温存） | 76.86 s |
| `JavaCodeCalculatorV3Test` | 82.69 s（同時稼働していた別ジョブの CPU 競合の影響が大きいと見られる。javac 自体のコストは本 PR の対象外） |
| `P4DslJavaCodeCalculatorClassicEngineTest` | 25.08 s |
| `P4AstEvaluatorCalculatorTest` | 5.07 s |
| `P4DslJavaCodeCalculatorTest` | 16.85 s |
| `P4AstEvaluatorCalculatorClassicEngineTest` | 57.45 s（timeout 無効化ずみの classic エンジン経路、本来的に重い） |

`AstEvaluatorCalculatorTest`・`JavaCodeCalculatorV3Test` 以外は軒並み単体 baseline（90〜113 s）から
大きく下がっており、キャッシュが機能していることが確認できる。ばらつきは主に「どのクラスが最初に
キャッシュを温めるか」と「計測時に他ジョブが同じホストの CPU を奪っていたか」に由来し、本変更が
狙う「6 回の重複を 1 回にする」効果とは別の要因である。

## 2. 原因の再診断

`CalculatorImplTest`（全バックエンド共通の基底クラス、49 個の `@Test`、約 150 個の distinct 式）の
`calc()` / `calcWithResult()` / `compileOnly()` は、それぞれ次の 2 段階を踏む:

1. `preConstructedCalculator(formula)` — バックエンド固有の構築（AST 評価器の構築、または DSL の
   Java コード生成 + `javac` コンパイル）。
2. `testAllMatch(calculator.getParser(), formula)` — **`calculator.getParser()` は全バックエンド共通で
   `Parser.get(FormulaParser.class)`（legacy の手書き PEG 文法）を返す**。つまりバックエンドが何であれ、
   同じ classic 文法で同じ式を毎回パースし直すだけの「回帰確認」。

`FormulaParser` は fraud-alert 級の深いネスト式（`if(...)` の多段ネスト、`|`/`&` の連鎖）で指数的に
バックトラックする（`P4DslJavaCodeCalculatorClassicEngineTest` のコメントにも明記されている既知の性質）。
`CalculatorImplTest` には 6 つの具象サブクラスがあり、**同じ ~150 式に対する classic 文法パースが
最大 6 回、内容的には無意味に繰り返されていた**。javac は `P4DslJavaCodeCalculatorTest` 系のみに
かかる追加コストで、実測では合計コストの一部（3 スイート比較で見た +15〜23 s 相当）にとどまり、
issue 本文が仮説とした「javac が支配的」は少なくともこのマシンでは当てはまらなかった
（負荷 15〜25 の共有ホストでは javac 呼び出し 1 件が 10 秒を超えると書かれており、そちらの環境では
javac コスト自体も比例して重くなるはずだが、いずれにせよ classic 文法の重複再検証は負荷に関わらず
常に 6 倍払っていたコストである）。

## 3. 実装した変更

`src/test/java/org/unlaxer/tinyexpression/CalculatorImplTest.java` のみ変更。プロダクションコード
（`org.unlaxer.tinyexpression.evaluator.*`、`org.unlaxer.compiler.*`）は一切変更していない。

- `verifyClassicGrammarAccepts(Parser, String)` を追加。`(parser のクラス, formula 文字列)` をキーにした
  JVM 静的な `ConcurrentHashMap.newKeySet()` で「classic 文法での検証は既に成功済みか」を記録する。
  - 初出の `(parser, formula)` は今まで通り `testAllMatch` を実際に呼び、成功したときだけキーを記録する
    （**失敗はキャッシュしない** — 本物の文法退行が起きた場合は今まで通り最初の遭遇で確実に失敗する）。
  - 既出のキーは `testAllMatch` を呼ばずに即 return する。
  - `calc()` / `calcWithResult()` / `compileOnly()` の 3 箇所全ての直接呼び出しを置き換えた。
- Surefire は既定で `reuseForks=true`（pom.xml、1 フォークを使い回す）なので、`mvn test` 1 回の実行内で
  6 つのサブクラスがこの静的キャッシュを共有する。ディスクへの永続化はしていない（`mvn test` を跨いだ
  再利用はしない、クリーンな実行の速度改善に閉じたスコープ）。

### なぜ javac のバッチ化／バイトコードキャッシュ（issue 本文の案）を採らなかったか

`JavaCodeCalculatorV2`/`DslJavaCodeCalculator` には既に「`precompiled-bytecode` モード」の
コンストラクタ（javaCode/byteCode を直接受け取り再コンパイルしない経路）があり、これをテスト層から
呼べれば javac 呼び出し自体を削減できる。ただし:

- 実測で javac の寄与は合計コストの支配項ではなかった（上記診断参照）。
- `var $name as string set ...; ...` のような複数文の式は依存クラス（`ClassNameAndByteCode` のリスト）を
  伴うことがあり、バイトコードキャッシュを安全に組むには依存解決も含めて再現する必要があって
  リスクの割に得られる追加削減が小さい。
- 本タスクの制約「エンジンの挙動を変えない」を最も安全に守れるのは、プロダクションのコンパイル経路に
  一切触れない今回の変更である。

javac 側の改善は、実測が示す「支配項ではない」という前提が変わった場合（例: より深い load でこの
マシンより javac 単体コストが相対的に増える場合）に別 issue で再検討する。

## 4. カバレッジが変わっていないことの確認

- 削除・`@Ignore` 追加をした `@Test` は無い。全 49 メソッド × 6 派生クラス = 294 テストは変更前と
  同じ本数・同じアサーションを実行する（`Tests run: 294, Failures: 0, Errors: 0, Skipped: 12` — skip 数も
  変更前と同じ、`testStringSlice`/`testTypeInference` の既存の条件付きスキップのみ）。
- `verifyClassicGrammarAccepts` はキャッシュ**ヒット時に検証をスキップする**が、ヒットするのは
  「同じ (parser クラス, formula 文字列) を過去に成功で検証済み」の場合のみ。あるスイートで初めて
  出てくる式は必ず実際にパースされ、アサートされる。文字列が 1 文字でも違えば別キーになるため、
  各スイート固有の式（バックエンド固有の className を式内に含むものは無い — 式自体はテキストとして
  共有）は正しく区別される。
- 失敗はキャッシュしないため、grammar 回帰が起きた場合は最初に遭遇したスイートで today 通り検出される。
- ローカルで `P4DslJavaCodeCalculatorTest,AstEvaluatorCalculatorTest,P4AstEvaluatorCalculatorTest,P4DslJavaCodeCalculatorClassicEngineTest,P4AstEvaluatorCalculatorClassicEngineTest,JavaCodeCalculatorV3Test`
  を実際に実行し、`Failures: 0, Errors: 0`、スキップ数も変更前の各単体実行の合計と一致することを確認した。

## 5. 未対応（issue #200 の受け入れ条件のうち）

- 「49 式 × backend の重複を parametrised 1 スイートに畳み、深い式は既定は代表 5 式・full は CI だけ」
  という構造変更は行っていない。本 PR のキャッシュだけで `P4DslJavaCodeCalculatorTest` は 60 秒目標を
  達成できたため、より侵襲的なテスト構造変更は見送った（1584 行の `CalculatorImplTest` を書き換える
  リスクに対して追加で得られる削減が小さい）。必要になれば別 issue で。
- parse timeout のロード依存スケーリング（受け入れ条件 4）は本 PR のスコープ外。既に
  `-Dtinyexpression.p4.parse.timeout.millis` で調整可能な仕組みがあり、今回の変更で重複コストそのものが
  減ったことで高負荷時のタイムアウト遭遇率も間接的に下がると見込まれるが、専用の対応はしていない。
